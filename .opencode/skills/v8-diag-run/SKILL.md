# /v8-diag-run — запуск 1С из консоли с перехватом ошибок

Платформа 1С под Linux при падении часто показывает модальное окно
«К сожалению, возникла непредвиденная ситуация» и **ждёт человека**, а код
возврата при этом может быть 0. Поэтому ошибка перехватывается не кодом
возврата, а **файлами-артефактами на каждом шаге**. Правило: у каждого запуска
есть минимум один файл, который появляется при успехе и (другой) при падении.

## Общее окружение

- Бинарь: `/opt/1cv8/x86_64/8.3.27.2342/1cv8` (в PATH как `1cv8`).
- GUI-режимы требуют X-сервер:
  `export DISPLAY=:0 XAUTHORITY=/run/user/1000/.mutter-Xwaylandauth.XXX`
  (актуальный суффикс — `ls /run/user/1000/.mutter-Xwaylandauth.*`; меняется
  после перезагрузки).
- Любой запуск — под `timeout -k 5 <сек>` (обычно 120–150): зависший модалкой
  сеанс иначе останется навсегда.
- Убить leftover-процесс: `pkill -x 1cv8` (точно `-x`; `pkill -f "1cv8 …"`
  убивает собственный shell).
- `/Out"<файл>"` — слитно, без пробела, путь в кавычках внутри аргумента.
  Лог пишется в UTF-8, часто одной строкой без переводов.

## Шаг 1. Сборка обработки из XML-исходников (DESIGNER)

Аргумент — **файл описания** `Пробник.xml`, а не каталог; второй позиционный —
куда положить EPF.

```bash
1cv8 DESIGNER /F<путь к базе> /DisableStartupDialogs \
  /LoadExternalDataProcessorOrReportFromFiles \
  <каталог>/tools/1c/diag/Пробник.xml /tmp/opencode/Пробник.epf \
  /Out"/tmp/opencode/build39.log"
```

Перехват ошибок сборки: смотреть **не** код возврата, а `/Out`-лог:
маркер успеха — `Import completed. Total time: …`; ошибки компиляции модулей
платформа пишет в этот же лог. EPF обязан появиться на диске —
`ls -la` после запуска.

## Шаг 2. Прогон на базе (ENTERPRISE /Execute)

```bash
timeout -k 5 150 1cv8 ENTERPRISE /F/home/anton/Documents/1C/DemoBPprof \
  /DisableStartupDialogs /Execute /tmp/opencode/Пробник.epf \
  /Out"/tmp/opencode/run39.log"
echo "exit=$?"
```

- В базе нет пользователей → запускать **без `/N`**: с `/N` платформа ответит
  «The infobase user is not authenticated» и кодом 1.
- Обработка в `/Execute` сама открывает форму, делает дело и закрывает сеанс
  (`ЗавершитьРаботуСессии`); взаимодействие с человеком исключено.

## Шаг 3. Как устроена обработка, чтобы падение было видно

Проверенный образец — `tools/1c/diag/Пробник/` (модуль формы
`Forms/Форма/Ext/Form/Module.bsl`, весь механизм в `ПриСозданииНаСервере`):

1. Главный `Попытка … Исключение` оборачивает всю работу. В `Исключение` —
   отдельным `Попытка` пишется **crash-файл** `Путь + ".crash.txt"` со строкой
   `незакрытое исключение: ОписаниеОшибки()`. Без этого незащищённая ошибка
   «вешает сеанс молча».
2. Итоговый снимок пишется в фиксированный путь
   `/tmp/opencode/diag_<ИмяКонфигурации>.txt` (`ЗаписьТекста`, UTF8,
   4-й параметр `Истина` — перезаписывать). Его наличие/mtime — признак успеха.
3. Секции собираются в структуру; каждая секция сама ловит свои ошибки и
   складывает текст в массив `Ошибки`, который печатается в конце снимка —
   частичный результат лучше никакого.
4. Каждая секция вызывает `Прогресс("<имя>")` — он пишет метку в отдельный
   файл (например `run36.log` допиской). Упавшая обработка остаётся с
   последней меткой: видно, **на какой секции** свет погас.
5. Тяжёлые тесты включаются **флаг-файлами** (`ФлагФайл("/tmp/opencode/run_bp_party.txt")`),
   которые создаёт shell перед прогоном: один и тот же EPF умеет разные режимы
   без пересборки.
6. Если снимок не записался даже в `Исключение` — пишется `Путь + ".error.txt"`.

## Шаг 4. Разбор результата (порядок проверки)

1. `ls -la /tmp/opencode/diag_*.txt*` — появился/обновился ли снимок, есть ли
   `.crash.txt` / `.error.txt` рядом.
2. Если снимка нет — `cat /tmp/opencode/run39.log` и `grep -i "непредвиденн\|исключ\|error" …`:
   сюда попадают и ошибки сервера, и текст фатального исключения.
3. `exit=124` от `timeout` — сеанс завис (обычно модалка). Это тоже ответ:
   база/платформа не переварила прогон; фиксировать как ограничение.
   Так УТ 11.5.22.186 падает при `/Execute` на платформе 8.3.27.2342, тогда
   как БП 3.0.208.14 работает (`cfg/EVIDENCE-2026-11-01-menu.md`, §6.3).
4. Нужно «видеть» экран зависшего сеанса — снимок окна `XGetImage`
   (`/tmp/opencode/xgrab.py`), текст через локальный tesseract
   (`/tmp/opencode/ocr`). Root-снимок под XWayland даёт чёрный экран,
   gdbus GNOME Shell — AccessDenied.

## Шаг 5. Если нужен техжурнал платформы

Глубже `/Out` — технологический журнал через переменную, имя которой
начинается с цифры (нужен `env`):

```bash
timeout 120 env "1C_TECH_LOG=/tmp/opencode/tech.log" \
  1cv8 ENTERPRISE "/F<база>" /N"Администратор" \
  /DisableStartupDialogs /DisableStartupMessages "$@"
```

Готовая обёртка — `/tmp/opencode/run1c.sh <ENTERPRISE|DESIGNER> <база> <техжурнал> [доп. аргументы…]`.

## Чего не делать

- Не полагаться на код возврата как на признак успеха.
- Не запускать без `timeout` — зависший `1cv8` блокирует следующую сборку той же базы.
- Не читать `/Out`-лог «на глаз» как OEM: файл UTF-8, но без переводов строк.
- Не писать результат работы в stdout — только в файл изнутри обработки.
