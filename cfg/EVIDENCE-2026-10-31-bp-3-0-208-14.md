и он не связан с УТ автоматически. Это уже не про обмен, это про структуру:
в бухгалтерии физически некуда положить характеристику и серию из строки УТ.

## 3. Как проводится: доля — это вес распределения количества

`Documents/КомплектацияНоменклатуры/Ext/ObjectModule.bsl`, `ОбработкаПроведения`
(строки 147–279) собирает две независимые таблицы — по комплектации и по
разукомплектации:

```
ТаблицаСписанныеТоварыКомплектация = УчетТоваров.ПодготовитьТаблицуСписанныеТовары(…);
ТаблицаКомплектующиеКомплектация  = УчетТоваров.ПодготовитьТаблицуКомплектующихКомплектация(…);

СписаниеТоваровРазукомплектацияТаблица =
    Документы.КомплектацияНоменклатуры.ПодготовитьТаблицуСписаниеТоваровРазукомплектация(…);
```

Дальше — НДС (`УчетНДСБП`, `УчетНДСРаздельный`), прослеживаемость
(`ПрослеживаемостьБП.СформироватьДвиженияРеализацияТоваров` и
`…ПоступлениеТоваров`), УСН (`НалоговыйУчетУСН`) и учёт ИП
(`УчетДоходовИРасходовПредпринимателя`). Если стоит `РучнаяКорректировка`,
процедура выходит сразу после подготовки наборов записей.

**Как именно работает доля при разукомплектации** —
`Documents/КомплектацияНоменклатуры/Ext/ManagerModule.bsl:542–565`:

```
Если ТаблицаСписания.Количество() = 0
    ИЛИ Реквизиты.Количество = 0
    ИЛИ Реквизиты.ВидОперации <> Перечисления.ВидыОперацийКомплектацияНоменклатуры.Разукомплектация Тогда
    Возврат ТаблицаСписания;
КонецЕсли;

МассивКоэффициентов = ТаблицаСписания.ВыгрузитьКолонку("ДоляСтоимости");

МассивРезультата = ОбщегоНазначенияБПКлиентСервер.РаспределитьПропорционально(
    Реквизиты.Количество, МассивКоэффициентов, 3);
Если МассивРезультата <> Неопределено Тогда
    ТаблицаСписания.ЗагрузитьКолонку(МассивРезультата, "Количество");
КонецЕсли;
```

Читается так: количество списываемого комплекта распределяется **пропорционально
долям строк**. То есть `ДоляСтоимости` в БП — не «процент себестоимости»,
а коэффициент, задающий, сколько единиц каждой комплектующей получено из одного
комплекта. При `Комплектация` эта же колонка не нужна, и
`ОбработкаПроверкиЗаполнения` снимает с неё обязательность.

Отсюда практический вывод для §4.2: формула ИТС «себестоимость комплектующей =
доля от себестоимости комплекта» и код БП согласуются, но работают через
количество: доля задаёт количество, количество — сумму по партии.

## 4. Приём `Документ.СборкаТоваров` из УТ: правило живёт в коде

### 4.1 Где регистрируется правило

`CommonModules/МенеджерОбменаЧерезУниверсальныйФормат13/Ext/Module.bsl`.
Общая процедура `ЗаполнитьПравилаКонвертацииОбъектов(НаправлениеОбмена,
ПравилаКонвертации)` (строка 492) регистрирует правило получения без всяких
условий по версии формата; вызов — строка 706:

```
ДобавитьПКО_Документ_СборкаТоваров_Получение(ПравилаКонвертации);
```

Само правило — строки 14375–14416:

```
ПравилоКонвертации.ИмяПКО                       = "Документ_СборкаТоваров_Получение";
ПравилоКонвертации.ОбъектДанных                 = Метаданные.Документы.КомплектацияНоменклатуры;
ПравилоКонвертации.ОбъектФормата                = "Документ.СборкаТоваров";
ПравилоКонвертации.ПослеЗагрузкиВсехДанных      = "ОтложеннаяОбработка_СборкаТоваров";
ПравилоКонвертации.ВариантИдентификации         = "СначалаПоУникальномуИдентификаторуПотомПоПолямПоиска";
…
ПравилоКонвертации.ПоляПоиска.Добавить("Дата,Номер");
```

То есть для пары «УТ 11.5 → БП 3.0» на штатных правилах вопрос «есть ли
правило приёма сборки/разборки» закрыт: **правило есть, оно в коде
конфигурации и включено всегда**. Это не макет из §7.1 файла по УТ
(тот относится к обмену через план обмена, механизм БП 2.0), а конвертация
по формату EnterpriseData.

`ПКО_Документ_СборкаТоваров_Получение_ПриКонвертацииДанныхXDTO`
(строки 34259–34315) читает `ДанныеXDTO.Товары` — то есть строки документа УТ,
а не какую-либо из его табличных частей `ВидыЗапасовСписание`/`ВидыЗапасовОприходование`:

```
ПравилаЗаполнения.Вставить("Номенклатура",          "Номенклатура");
ПравилаЗаполнения.Вставить("Количество",            "Количество");

ПравилаЗаполнения.Вставить("ДоляСтоимости",         "ДоляСтоимости");
ПравилаЗаполнения.Вставить("ИдентификаторСтроки",   "ИдентификаторСтроки");
ПравилаЗаполнения.Вставить("КоличествоРНПТ",        "КоличествоПрослеживаемости");
ПравилаЗаполнения.Вставить("ПрослеживаемыйТовар",   "ПрослеживаемыйТовар");
```

Дальше — `ЗаполнитьГТДИПрослеживаемость(...)` (номер ГТД и РНПТ),
`НормироватьДолюСтоимости(МассивСтрокТовары)` и перенос в
`ДополнительныеСвойства` (`Комплектующие`, `СведенияПрослеживаемости`).

`НормироватьДолюСтоимости` (строки 48301–48330) — тонкое место:

```
МаксимальноеКоличествоЗнаковПослеЗапятой = …максимум по всем строкам…;
КоэффициентДляПриведенияКНорме = 1;
Для НомерИтерации = 1 По МаксимальноеКоличествоЗнаковПослеЗапятой Цикл
    КоэффициентДляПриведенияКНорме = КоэффициентДляПриведенияКНорме * 10;
КонецЦикла;
…
СтрокаТовары.ДоляСтоимости = СтрокаТовары.ДоляСтоимости * КоэффициентДляПриведенияКНорме;
```

Потому что `ДоляСтоимости` в БП — целое Число(10,0), а в формате `ТипДоля` —
`xs:decimal totalDigits="10" fractionDigits="3"`. Если УТ пришлёт `0,333`,
БП получит `333`. УТ 11.5 штатно шлёт целые (`ВЫРАЗИТЬ(… КАК ЧИСЛО(10,0))`),
но при доработках и чужих правилах это первое, что поедет.

### 4.4 Что происходит при повторной загрузке

`ПКО_Документ_СборкаТоваров_Получение_ПередЗаписьюПолученныхДанных`
(строки 34316–34351) при обновлении существующего документа сопоставляет строки
по ключу и сохраняет счета:

```
МассивКлючевыхПолей.Добавить("Номенклатура");
МассивКлючевыхПолей.Добавить("Количество");
МассивКлючевыхПолей.Добавить("ДоляСтоимости");
МассивКлючевыхПолей.Добавить("НомерГТД");
МассивКлючевыхПолей.Добавить("СтранаПроисхождения");
МассивКлючевыхПолей.Добавить("ПрослеживаемыйТовар");

ЗаполнитьТабличнуюЧастьОбъектаНачальнымиДанными(
    ПолученныеДанные.Комплектующие, ДанныеИБ.Комплектующие,
    МассивКлючевыхПолей, "СчетУчета,СпособУчетаНДС");
…
УстановитьОтменуПроведенияДляРучнойКорректировки(ДанныеИБ);
```

Практический смысл: если бухгалтер поправил в импортированном документе счета
учёта и способ учёта НДС, повторная загрузка их не затрёт — они переносятся
из прежней версии документа по совпадению ключевых полей.

### 4.5 Дозаполнение после загрузки

`ОтложеннаяОбработка_СборкаТоваров` (строки 51306–51352) выполняется после
загрузки всех данных:

```
ПрослеживаемыйТовар = Объект.Комплектующие.НайтиСтроки(Новый Структура("ПрослеживаемыйТовар", Истина));
ЕстьПрослеживаемыйТовар = ПрослеживаемыйТовар.Количество() <> 0;
Если ЕстьПрослеживаемыйТовар Тогда
    Объект.ПрослеживаемыйКомплект = Истина;
    УстановитьПрослеживаемыйКомплектВНоменклатуре(КомпонентыОбмена, Объект.Номенклатура);
КонецЕсли;
```

Дальше — счета и способ учёта НДС по шапке и по каждой строке
(`БухгалтерскийУчетПереопределяемый.ПолучитьСчетаУчетаНоменклатуры`), с
подстановкой `ПринимаетсяКВычету`, если ничего не нашлось.

### 4.6 Комиссионные товары уходят другим документом

`ПОД_Документ_СборкаТоваров_Получение_ПриОбработке` (строки 33217–33225):

```
ИспользованиеПКО.Документ_СписаниеПриСборке_Получение = Ложь;
Для Каждого СтрокаТовары ИЗ ДанныеXDTO.Товары Цикл
    Если ЗначениеЗаполнено(СтрокаТовары.ТипЗапасов) И СтрокаТовары.ТипЗапасов.Значение = "КомиссионныеТовары" Тогда
        ИспользованиеПКО.Документ_СписаниеПриСборке_Получение = Истина;
        Прервать;
    КонецЕсли;
КонецЦикла;
```

Правило `Документ_СписаниеПриСборке_Получение` (строки 14675–14717) пишет
`Документ.СписаниеТоваров` с ТЧ `Товары` (`ЕдиницаИзмерения`,
`ИдентификаторСтроки`, `Количество`, `Коэффициент`, `Номенклатура`, `НомерГТД`,
`ПрослеживаемыйТовар`, `СтранаПроисхождения`, `СчетУчета`) и ТЧ
`СведенияПрослеживаемости`. То есть одна и та же операция УТ может дать в БП
**два** документа — `Комплектация номенклатуры` и `Списание товаров`.
Это подтверждает §5.3: назначений в БП минимум два, и решает их склад/тип запасов.

## 6. Планы обмена и правила в БП

| План обмена БП | Объектов в составе | `Document.КомплектацияНоменклатуры` | `Catalog.СпецификацииНоменклатуры` | Макеты правил |
|---|---|---|---|---|
| `СинхронизацияДанныхЧерезУниверсальныйФормат` | 76 | **нет** | есть | нет |
| `ОбменУправлениеТорговлей103БухгалтерияПредприятия30` | 71 | есть | **нет** | `ПравилаОбмена`, `ПравилаОбменаКорреспондента`, `ПравилаРегистрации` |

Два вывода, которые важны для §5.3 и §5.4.

1. В составе плана синхронизации БП документа комплектации **нет**: он не
   выгружается из БП, он только принимается — по правилу из §4.1, которое
   привязано к типу формата, а не к составу плана. Отсутствие строки в составе
   плана не мешает приёму и не означает «не поддерживается».
2. Макеты правил в БП есть только для старого коннектора УТ 10.3
   (`ОбменУправлениеТорговлей103БухгалтерияПредприятия30`, строк
   «СборкаТоваров» — 0, «КомплектацияНоменклатуры» — 14, из них два
   соответствия вида операции `Комплектация → Комплектация` и
   `Разукомплектация → Разукомплектация`). Для пары УТ 11.5 → БП 3.0 макетов
   правил в БП нет вовсе: правила живут в коде, как показано в §4.

## 7. Что при приёме теряется — сводка

| Что | Почему | Следствие |
|---|---|---|
| `Характеристика`, `Серия`, `Упаковка` строки | в БП нет таких колонок в документе | комплект с характеристиками разберётся «по номенклатуре», детализация потеряется |
| `НДС в стоимости` | принудительно `НеИзменять` | НДС не пересчитывается при загрузке |
| счета учёта и способ учёта НДС УТ | берутся из настроек БП (`ПолучитьСчетаУчетаНоменклатуры`) | расхождение счетов между базами не лечится обменом |
| `Подразделение` | уходит в дополнительные свойства | ищется в доп. реквизитах, не в реквизите документа |
| себестоимость и суммы строк | в формате их нет как самостоятельных полей | считаются при проведении по данным БП |
| `Статус`, `ЗаказНаСборку`, `ВариантПриемкиТоваров` | нет в приёмнике | управленческий контур УТ в БП не переносится |
| комиссионные строки | уходят в `Списание товаров` | один документ УТ → два документа БП |

## 8. Что из этого следует для книги

1. **§5.4 меняет формулировку.** Вопрос не «есть ли правило для разборки»,
   а «дошёл ли документ и заполнился ли вид операции». Приём разборки в БП
   реализован кодом штатно: `Документ.СборкаТоваров` → `Комплектация
   номенклатуры`, `Разборка` → `Разукомплектация`, во всех версиях формата.
   Практика сообщества (§5.4, отчёты 04 и 07) этому не противоречит: она
   описывает либо ненастроенный узел, либо другой коннектор/релиз.
2. **§5.3 получает точные имена полей.** Таблица маппинга теперь может
   показывать не только «вид операции», но и что именно ложится в
   `Комплектующие` и чего там нет.
3. **§4.2 нужно уточнить.** Доля в БП — коэффициент распределения количества
   (`РаспределитьПропорционально`), а не только «процент себестоимости».
4. **§4.4 подтверждается кодом.** Счёт по умолчанию — из вида номенклатуры;
   при загрузке счета дозаполняются, а при повторной загрузке сохраняются
   из прежней версии документа.
5. **§4.5 нужно дополнить.** Проводки есть только в `Хозрасчетный`;
   остальные 14 движений — НДС, УСН, ИП и прослеживаемость. Отдельного
   складского регистра у документа нет.
6. **§8.3 пополняется первоисточником.** Разбор БП — такой же проверяемый
   источник, как разбор УТ.

## 9. Чего эта выгрузка не показывает

* настройки конкретного узла синхронизации и загруженные в него правила;
* проводки Дт/Кт — регистр `Хозрасчетный` описан метаданными, а суммы и счета
  в нём — данные;
* фактическую себестоимость и остатки;
* поведение на живых данных: как именно разберётся комплект с
  характеристиками и сериями, видно только в паре баз (тест ТК-3).
