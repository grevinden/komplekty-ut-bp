## 1. Принадлежность строки набору в УТ

В документе `РеализацияТоваровУслуг` у строк есть три «наборных» реквизита:
`НоменклатураНабора`, `ХарактеристикаНабора`, `АналитикаУчетаНаборов`. На
документе `ТД00-000007` (набор «Мебельный гарнитур "Артон"» + услуга
«Доставка товара», 03.11.2026) запрос по регистру выручки и себестоимости
показал заполнение по всем четырём товарным строкам и пустое значение у
услуги:

```
АналитикаУчетаНоменклатуры=Кровать; Мебельный склад |
АналитикаУчетаНаборов=Мебельный гарнитур "Артон";  | ... | ТипЗапасов=Собственный товар

АналитикаУчетаНоменклатуры=Доставка товара; Мебельный склад |
АналитикаУчетаНаборов= | ... | ТипЗапасов=Работа (Услуга)
```

То есть **в торговле принадлежность есть и она явная** — ссылка на набор, а не
догадка по составу. Услуга набора в этой аналитике не участвует.

Прямой запрос по ТЧ документа `ТД00-000007` (03.11.2026) уточняет, какие именно
реквизиты заполнены:

```
Товар=Доставка товара      | Набор=                      | ХарНабора= | Аналитика=
Товар=Кровать              | Набор=Мебельный гарнитур "Артон" | ХарНабора= | Аналитика=Мебельный гарнитур "Артон";
Товар=Туалетный столик     | Набор=Мебельный гарнитур "Артон" | ХарНабора= | Аналитика=Мебельный гарнитур "Артон";
Товар=Тумбочка прикроватная| Набор=Мебельный гарнитур "Артон" | ХарНабора= | Аналитика=Мебельный гарнитур "Артон";
Товар=Шкаф 3-дверный       | Набор=Мебельный гарнитур "Артон" | ХарНабора= | Аналитика=Мебельный гарнитур "Артон";
```

`НоменклатураНабора` — ссылка на набор, `АналитикаУчетаНаборов` — её
представление, `ХарактеристикаНабора` в этом примере не используется. Снимок:
[`tools/1c/diag/out/komplekt/ut-stroki-nabora-2026-11-03.txt`](../tools/1c/diag/out/komplekt/ut-stroki-nabora-2026-11-03.txt).

## 2. Что из этого доезжает до БП

Сообщение обмена `EnterpriseData/1.20`
(`/tmp/opencode/exch/files/Message_f62195a3-…_c7214224-….xml`, выгрузка
03.11.2026 22:12) содержит в строке реализации **11 полей**:

```
НомерСтрокиДокумента, ДанныеНоменклатуры, ЕдиницаИзмерения, Количество,
Сумма, Цена, КоличествоУпаковок, СтавкаНДС, СуммаНДС, ТипЗапасов,
ИдентификаторСтроки
```

Ни `НоменклатураНабора`, ни `ХарактеристикаНабора`, ни
`АналитикаУчетаНаборов`, ни `ВерсияДанных` в сообщении нет (0 вхождений по
файлу). `ТипЗапасов` у строк набора — `СобственныеТовары`, такой же, как у
обычной продажи товара: пометки «это строка набора» в нём нет.

Причина не в правилах конкретной пары, а в составе плана обмена: справочник
`ВариантыКомплектацииНоменклатуры` (там лежит состав набора) в план
`ОбменУправлениеТорговлейБухгалтерияПредприятия` не входит, а в БП у него нет
приёмника. Реквизиты строки, не описанные правилом конвертации, не выгружаются
по определению ([§5.1](../docs/05-perenos-dannyh.md#5.1)).

## 3. «Версия объекта» средствами платформы

Проверено на номенклатуре «Мебельный гарнитур "Артон"» (товар `00-00000016`),
на одноимённом наборе (`ЦУ-00000069`, артикул А-90) и на варианте комплектации
«Состав набора (4)».

| Проверка | Результат |
|---|---|
| `Ссылка.ВерсияДанных()` — **метод** | ошибки: `Object method not found (ВерсияДанных)` |
| `Ссылка.ВерсияДанных` — **свойство** | работает: `AAAACwAAAAA=` (товар), `AAAAAQAAAKQ=` (набор), `AAAAAgAAAAA=` (вариант) |
| поле запроса `ВерсияДанных` | есть, отдаёт то же значение |
| `ИсторияДанных.ПолучитьНастройки(Справочники.Номенклатура)` | `не настроена` |
| `Объект.ОбменДанными.Получатели` | `НаборУзлов` (объект в плане обмена) |

Версия меняется при **записи самого объекта** и растёт на единицу:

```
номенклатура «Артон»: до AAAACwAAAAA=, после AAAADAAAAAA= | изменилась: да
вариант «Состав набора (4)»: до AAAAAgAAAAA=, после AAAAAwAAAAA= | изменилась: да
версия набора после записи варианта: AAAAAQAAAKQ=   (не изменилась)
```

Три вывода, которые важны для схемы:

1. **«Версия ссылки» в платформе есть** — это свойство `ВерсияДанных` (не
   метод), доступное и в запросе. Значение — непрозрачная строка из 8 байт;
   для сравнения «менялся объект или нет» её достаточно, для чтения человеком
   она бесполезна.
2. **Версия набора не связана с составом.** Состав лежит в отдельном объекте —
   варианте комплектации. Запись варианта поднимает версию варианта, но версия
   номенклатуры-набора остаётся прежней. Значит «версия набора» как версия
   ссылки на набор не изменится, даже если поменять весь состав.
3. **Версия не передаётся в обмен** — ни версия набора, ни версия варианта
   (см. §2). В БП сравнивать нечего.

## 4. Отрицательные проверки

| Что проверяли | Результат |
|---|---|
| `ВерсияДанных` как метод ссылки | метода нет (свойство, а не метод) |
| `ИсторияДанных` для номенклатуры | механизм не настроен; это отдельная подсистема «История данных» с хранением снимков объектов, к обмену не относится |
| `ВерсияДанных` в сообщении обмена | 0 вхождений в обоих направлениях |
| `ВариантыКомплектацииНоменклатуры` в плане обмена | не входит, приёмника в БП нет |
| Пометка набора в `ТипЗапасов` строки | нет: у строк набора `СобственныеТовары` |
| Название набора в сообщении | приходит только в `Комментарий` документа, если его туда вписал человек |

## 5. Вывод

- Принадлежность товара набору **в УТ определяется точно** (ссылка набора в
  строке), а **в БП — только по составу**: пометка не приезжает.
- «Версия» как платформенное свойство существует, но к составу набора не
  привязана и в обмен не входит. Поэтому в БП версию надо определять самому —
  по отпечатку состава (номенклатура + количество), а её номер вести в реестре.
- Следствие для проектного решения: постобработка в БП без правки обмена
  опирается на **совпадение состава**, а не на ссылку. Это работает, но требует
  реестра составов и даёт риск ложного срабатывания, когда те же товары проданы
  не набором. Если риск неприемлем, единственная альтернатива — передавать в
  сообщении ссылку набора, то есть менять правила обмена (не расширение БП).
