## 2. D1 (P0). Свёртка не компилируется на сервере

```
{КомплектыОбмен ОбщийМодуль.КомплектыОбмен_Свертка.Модуль(323,2)}: Keyword Except expected
	<<?>>КонецПопытки; (Verification: Server)
```

Фрагмент (`КомплектыОбмен/CommonModules/КомплектыОбмен_Свертка/Ext/Module.bsl`):

```bsl
321:	Попытка
322:		СтрокаРезультат.Вставить("ЕдиницаИзмерения", Первая["ЕдиницаИзмерения"]);
323:	КонецПопытки;
```

Блок `Попытка` не имеет `Исключение` — синтаксическая ошибка. Она есть и в
`.cfe` из `dist/` (дамп `/tmp/opencode/dump-obmen`, тот же текст), т.е.
установленное расширение тоже нерабочее.

**Почему не замечалось:** `/CheckModules -ThinClient` серверный модуль
пропускает — там «No syntax errors found!». Серверные и внешние модули
проверяются только режимами `-Server` / `-ExternalConnection`. Живой вызов
подтверждает: `Выполнить("КомплектыОбмен_Свертка.ОбработатьДокумент(…);")`
не возвращает управление (модальное окно ошибки, `timeout 124`) — компиляция
падает, а не логика.

**Правка:** добавить `Исключение` (пустой обработчик, как в соседних блоках
309–320) либо убрать `Попытка` целиком — оба варианта эквивалентны.
**Замечание по процессу:** в `publish`-гейт добавить `-Server` и
`-ExternalConnection` — иначе класс ошибки повторится.

## 3. D2 (P0). Пометка не уходит из УТ

### 3.1. Факты

1. **В источнике пометка есть.** УТ, `РеализацияТоваровУслуг` `ТД00-000001`
   от 05.11 8:20 — у всех 4 строк заполнен `НоменклатураНабора` =
   «Мебельный гарнитур "Артон"».
2. **В сообщении пометки нет.** Архивное сообщение 04.11 21:20 (201 619 б,
   `/tmp/opencode/exch/files-archive-20261105/`): **0** вхождений подстроки
   «комплект» в любом регистре и **0** использований нашего namespace
   `…/edi_stnd_ext_enterprisedata/EnterpriseData/1.20`.
   Текущее исходящее сообщение (84 884 б) — «объектов в теле: нет» вообще.
3. **Значит, свёртка в БП ни разу не выполнялась.** Документ `ТД00-000001` в БП
   до сих пор содержит 4 строки-компонента (Кровать 4 500 / Туалетный столик
   1 950 / Тумбочка 2 880 / Шкаф 4 800), в `Комментарий` метки
   «Комплекты: обработано» нет. Журнал `КомплектыБП_ЖурналОбработки` — одна
   запись: `Документ` пуст, `КлючГруппы` = `?`, `Состояние` = `Ошибка`,
   `Сообщение` = «Исключение: Too many actual parameters» (до прогона
   14:20 — «Type mismatch (parameter number '1')»).

### 3.2. Где искать причину

Ветка записи XDTO в `КомплектыУТ/CommonModules/МенеджерОбменаЧерезУниверсальныйФормат`:

- 8–34 — хук `&После("ДобавитьПКО_Документ_РеализацияТоваровУслуг_Отправка")`
  добавляет три свойства в ПКО **отправки**;
- 36–142 — хук `&После("ПКО_Документ_РеализацияТоваровУслуг_Отправка_ПриОтправкеДанных")`
  группирует строки по `НоменклатураНабора` (стр. 56) и пишет значения;
- 120–122 — запись идёт **прямым присвоением**:
  `СтрокаXDTO.КомплектыОбмен_НаборУИД = УИД;` Присвоение необъявленного
  свойства XDTO-объекта даёт исключение;
- 125–134 — резервная ветка через `УстановитьРасширенноеСвойствоXDTO`;
- 148–158 — в этой резервной ветке используется **неопределённая переменная**
  `ФабрикаXDTO` (стр. 153): исключение проглатывается пустым `Исключение`,
  свойство не устанавливается никогда;
- всё тело обоих хуков обёрнуто в `Попытка … КонецПопытки` без диагностики —
  любая ошибка не оставляет следа.

Дополнительно: хук `ПриОтправкеДанных` вызывается только при
`СтекВыгрузки.Количество() <= 1` (стр. 40–42) — при вложенной выгрузке
комплекта пометка не ставится вообще.

**Что проверено и чего это не доказывает.** Прямой вызов обоих «целевых»
методов из обработки даёт `Object method not found`. Это **не** доказывает
отсутствие метода: внутренние процедуры модуля не экспортные, снаружи они
не видны. Вопрос «срабатывает ли `&После` вообще» остаётся открытым и
закрывается только диагностикой (см. шаг 2.1 плана).

### 3.3. Правка

1. Диагностика: временный журнал (или запись в регистр) на входе и выходе
   каждого хука — установить, вызывается ли хук и на каком шаге падает.
2. Писать свойства штатным путём: через `ФабрикаXDTO` из `КомпонентыОбмена`
   (проверив, что такое свойство есть в структуре) либо через
   `ОбменДаннымиXDTOСервер`-API; каждую установку — с логированием ошибки,
   а не с пустым `Исключение`.
3. Согласовать имена: одно имя свойства на пару баз, например
   `КомплектыОбмен_НаборУИД` в **обоих** менеджерах (см. D7).
4. `КоличествоНаборов` — из данных строки, а не константа `1` (см. D8).

## 5. P1. Потеря данных и ложный успех

### 5.1. D4 — строки неуспешной группы исчезают

`КомплектыОбмен_Свертка`, шаги 4–5:

- 102–114: по каждой группе вызывается `ОбработатьОднуГруппу`; при `Успех`
  строка комплекта попадает в `ВсеСтрокиЗамены`, иначе только текст в
  `Результат.Ошибки`;
- 117: `Товары.Очистить();`
- 120–123: добавляются строки комплектов;
- 125–130: добавляются «обычные» строки из `НеГрупповыеСтроки`.

Строки **неуспешной** группы не попадают ни в один из двух списков. Итог:
товар пропал из документа, `СуммаДокумента` пересчитана меньше, пользователь
видит только запись в журнале. Для финансового документа это потеря данных,
поэтому P1, а не P2.

**Правка:** при неуспехе группы оставлять её строки в `Товары` как обычные
(добавлять `СтрокиГруппы` в конец), а ошибку — в журнал и в комментарий.

### 5.2. D5 — пустая сборка при отсутствии склада

`КомплектыОбмен_Карточки` 167–169: если склад не заполнен ни в продаже, ни в
настройках — `Возврат Документы["КомплектацияНоменклатуры"].ПустаяСсылка();`.
`КомплектыОбмен_Свертка` 221 ставит `Рез.Успех = Истина` безусловно, поэтому
группа считается обработанной, а спецификация пишется без сборки. При этом
`docs/11` §11.5 честно предупреждает про «первый склад по наименованию», но
про этот сценарий молчит.

**Правка:** отсутствие склада — ошибка группы (`Успех = Ложь`,
`Сообщение = "Не заполнен склад для сборки"`), а не тихий пропуск.

## 6. P2. Устойчивость, журнал, мёртвый код

- **D6. Журнал до записи документа.** `КомплектыБП_Обмен.ОбработатьПередЗаписью`
  пишет журнал (стр. 44–48) в момент, когда `ПолученныеДанные` ещё не записан.
  ЗаписатьЖурнал (стр. 141–181) берёт `ПолученныеДанные["Ссылка"]`, у
  незаписанного объекта она пустая (стр. 150–156), а `КлючГруппы` при
  отсутствии результата группы — литерал `"?"` (стр. 158). Поэтому все записи
  по группам схлопываются в одну строку с пустым документом. Подтверждено
  живой выборкой: в регистре ровно одна запись с пустым документом.
  **Правка:** писать журнал из `&После` записи документа (или отложенно —
  накапливать и сбрасывать после успешной записи), ключ группы делать
  измерением осмысленно (УИД + номер строки).
- **D7. Асимметрия wire-имён.** УТ: `ДобавитьПКС(СвойстваТЧ, "", "КомплектыОбмен_НаборУИД", 1, "", URI)`
  (свойство формата пустое, имя — наше); БП:
  `ДобавитьПКС(СвойстваТЧ, "КомплектыБП_НаборУИД", "", 1, "", URI)` (наоборот).
  Даже когда запись заработает, БП будет искать другое имя. **Правка:** одно
  имя на пару, симметричные вызовы; заодно обновить §11.2/§11.3.
- **D8. `КоличествоНаборов` = 1** (УТ, стр. 122) — при продаже двух наборов
  свёртка получит неверное количество. Данные для правильного значения в
  строке есть (`НоменклатураНабора` + количество), нужно согласовать правило
  пересчёта.
- **D9. Мёртвый код.** `ИндексыГрупп` (Свертка 42–47) заполняется, нигде не
  читается; `СтавкиНДС` (52/61/89) — задел под `РазделятьПоСтавкамНДС`, не

## 10. Открытые вопросы и риски

- **Изоляция `CheckModules` между расширениями.** `-Server` для `КомплектыБП`
  даёт `Variable is not defined (КомплектыОбмен_Сервер)`, хотя в живой базе
  `КомплектыБП_Обмен.ОбработатьПередЗаписью(Неопределено)` выполняется без
  ошибки. Значит, `CheckModules` проверяет расширение в отрыве от остальных —
  **нельзя** делать вывод о работоспособности пары по одному `CheckModules`;
  критерий 1 дополняется живым вызовом.
- **Хуки `&После` в УТ.** Не подтверждено, что они вообще вызываются: целевые
  методы не экспортные, прямой вызов снаружи невозможен. Закрывается только
  диагностикой (этап 2), поэтому оценка этапа 3 — вилка.
- **Регистрация изменений.** Текущее сообщение пустое по объектам; возможно,
  продажа не попадала в регистрацию на выгрузку. Это надо проверять до любых
  выводов о wire-именах.
- **Склад «первый по наименованию».** Остаётся недетерминированным в базе с
  несколькими складами; в плане не меняем (осознанное упрощение прототипа),
  но в §11.7 это уже оговорено.
- **Незакоммиченное.** В `tools/1c/diag/Обмен/.../Module.bsl` добавлен режим
  `ПРОБА` (вычисление/выполнение выражений с подробным стеком ошибок) — им
  сняты доказательства §2–§3. Инструмент полезен для всех дальнейших проверок;
  решение о коммите — за владельцем.
